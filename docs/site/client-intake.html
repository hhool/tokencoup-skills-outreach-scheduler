Client intake & operations handbook

Client intake & operations handbook

Purpose: define what a client must provide, how the system feeds back operating status, and the internal business process from intake to steady state. Validated against three simulated client profiles (§3).

Chinese version: see client-intake.zh.md.

1. Client intake checklist

1.1 Required (kickoff blocked without these)

# Item Maps to system Notes
1 Domain (promotion target) project.domain one project per domain
2 Promotion scope: whole site now, specific pages later project.tags + level-1/2 URL list (asset page) per-page/product promotion = a later phase adding landing URLs; scope changes are just asset updates, no new project
3 Client operational mailbox wave2 sender identity + directory-site registrations email address plus SMTP/IMAP app-password credentials (or the client sends manually); credentials go to gitignored env file, never in the repo
4 Site TDK (title / description / keywords) asset tdk if not provided, system probes homepage meta; if probing fails → flagged missing in the daily report for manual fill
5 Level-1/2 page URLs to promote (manual list) asset page manual input only; absent → submissions land on the homepage
6 Brand basics: brand/maker name, one-line intro, logo URL form fields, outreach signature probed from the site if absent

1.2 Optional (defaults exist)

# Item Default when absent
7 Blog article list (guest_post bodies) sitemap/RSS harvest; still nothing → site-summary article generated from the site's own summary
8 Outreach email copy preferences (tone, signature) generic outreach email template
9 Exclusion list (site types / competitors not to touch) empty
10 Daily quota preference system default (per-project 10/day)
11 Report recipients (client-facing) report only lands in run_log; enable by configuring report.email

2. Operating status feedback (client-facing loop)

Two report layers, both from the same run_log — nothing is reported that is not already recorded:

Layer Cadence Content
Daily report (internal, §8 of DESIGN.md) daily, auto today's plan / yesterday's results / pending-confirmation queue / pool changes / human-action items
Client report (filtered daily report) configurable (daily or weekly digest) submissions made, successes/failures, live link list, assets on template fallback (quality signal), decisions needed from client

Key notifications that always reach the client regardless of cadence: - first live backlink for the project - weekly digest (volume, success rate, new live links) - anomalies: domain blocks, email bounces, path changes on reused submit endpoints

Recipient empty = no send (run_log only), same fail-open rule as the internal report.

4. Internal business process (intake → steady state)

① intake         client provides checklist §1.1 (+ any §1.2)
                 ↓
② verification   domain reachable? TDK probe? mailbox SMTP/IMAP login test?
                 page URLs return 200? → problems reported before kickoff
                 ↓
③ project setup  create project + assets (provided / probed / template),
                 tags, quota, exclusions
                 ↓
④ matching       pool × project → score → pending-confirmation queue
                 ↓  (human gate: select/confirm)
⑤ scheduling     confirmed items fill future dates by daily_quota
                 ↓
⑥ execution      cron: wave1 HTTP form submit; wave2 SMTP send;
                 captcha tiering; results → run_log
                 ↓
⑦ feedback       daily report (internal) + client report (filtered);
                 anomalies flagged
                 ↓
⑧ review loop    live-rate / failure-rate review → adjust quota,
                 templates, exclusions → back to ④

Step ownership: ①② are human (sales/ops), ③④⑤⑥⑦ are system with the single human gate at ④, ⑧ is human strategy on system data.

5. Gaps this simulation surfaced → design notes

  1. Multi-client sender identity: wave2 SMTP credentials are currently one global env file. With three clients, per-project sender identity (name + email + credentials path in projects/<domain>.yaml) is needed if each client uses its own mailbox. Default if unspecified: the shared ops mailbox.
  2. Client report recipient: report.email in project YAML (per-project), falling back to global config — already fits the config model.
  3. Client A phase-2 needs no schema change: it is just new entries in the page asset. Matching treats them as higher-priority landing URLs (fresh entries get a recency boost in scoring — to be confirmed in Phase 3).
  4. Client mailbox roles (ratified from real usage): a client mailbox carries two distinct business roles —
  5. registration role: brand identity for directory/form submissions (lands in the contact-email asset, used by wave1 forms and CUA fills, and as wave2 sender identity);
  6. summary role: recipient of periodic data digests (client report / daily report, report.email). One mailbox may serve both roles at once (current azgames practice: one Gmail does registrations and receives the digests). The config model already supports this — the same address can appear in contact-email and report.email; splitting into two mailboxes later is a config-only change, no schema impact. Client mailboxes are user data: credentials live in gitignored env files, addresses never in the repo.

客户接入与运营手册

客户接入与运营手册

目的：定义客户需要提供哪些资料、系统如何反馈运营状态、从接入到稳态的内部业务流程。已用三个模拟客户档案（§3）做校验。

英文版见 client-intake.md。

1. 客户资料清单

1.1 必需（缺一不开工）

# 资料项 对应系统 说明
1 域名（推广对象） project.domain 一域名一项目
2 推广范围：先推整站、后推具体页面 project.tags + 一级/二级地址清单（资产 page） 后期按页面/产品推广 = 在地址清单里加落地页，属资产更新，不用新建项目
3 客户运营邮箱 wave2 发件身份 + 目录站注册邮箱 邮箱地址 + SMTP/IMAP 应用专用密码凭据（或客户自发送）；凭据进 gitignored env 文件，永不入库
4 站点 TDK（title/description/keywords） 资产 tdk 不提供则系统探测首页 meta；探测失败 → 日报标 missing 提醒人工补
5 要推的一级/二级地址（人工清单） 资产 page 仅人工输入；缺失则提交一律落首页
6 品牌基础：品牌名/maker 名、一句话介绍、logo 地址 表单字段、外联署名 缺失则从站点探测

1.2 可选（有默认兜底）

# 资料项 缺省兜底
7 博文文章清单（guest_post 正文） sitemap/RSS 收割；仍无 → 站点摘要文章（由站点自身摘要生成）
8 外联邮件文案偏好（语气、署名） 通用外联邮件模板
9 排除清单（不投的站点类型/竞品） 空
10 每日配额偏好 系统默认（每项目 10 条/天）
11 报告收件人（对客户） 只落 run_log 不发送；配置 report.email 后启用

2. 运营状态反馈（面向客户的闭环）

两层报告，同源于 run_log——没记录的不汇报：

层 频率 内容
日报（内部，DESIGN.md §8） 每天自动 今日计划 / 昨日结果 / 待确认队列 / 池变化 / 待人工事项
客户报告（日报过滤版） 可配置（每日或每周摘要） 提交量、成功/失败、已上线链接清单、靠模板兜底的资产数（质量信号）、需客户拍板事项

无论频率如何、必达客户的节点通知： - 项目首个外链上线 - 每周摘要（量、成功率、新增上线链接） - 异常：域名被封、邮件退信、复用提交路径变更

收件人空 = 不发送（仅落 run_log），与内部报告同一 fail-open 规则。

3. 模拟客户档案（校验用例）

客户 A — 游戏门户 客户 B — 童车评测 客户 C — 音效工具
域名 games-portal.example kids-bike-reviews.example sound-tools.example
目标 获取流量；一期整站，二期具体游戏页（如 Crossy Road、2048 Couch Lazy） 获取流量 获取流量
分类标签 gaming, browser-games, english parenting, balance-bike, english tools, sound, english
二期机制 把游戏落地页加进 page 资产清单——匹配打分自动把它们当作落地 URL 候选；无需新建项目 — —
预计通道 wave1 表单直投（游戏/应用目录）+ wave2 邮件 wave1 + wave2（亲子博客、客座文章） wave1（工具目录）

模拟校验了什么： - 一域名一项目，推广范围靠资产演进（A 的两期） - 分类标签按市场驱动匹配（B 亲子 vs C 工具 vs A 游戏） - 资产兜底链按客户生效：A/B/C 各自缺的资产不同，各走各的兜底

4. 内部业务流程（接入 → 稳态）

① 接入           客户提供 §1.1 清单（+ 任意 §1.2 可选项）
                 ↓
② 核验           域名可达？TDK 探测？邮箱 SMTP/IMAP 登录测试？
                 页面地址返回 200？→ 问题在开工前报出
                 ↓
③ 建档           建项目 + 资产（provided / probed / template）、
                 标签、配额、排除清单
                 ↓
④ 匹配           池 × 项目 → 打分 → 待确认队列
                 ↓  （人工闸：勾选确认）
⑤ 排期           确认项按 daily_quota 填充未来日期
                 ↓
⑥ 执行           cron：wave1 HTTP 表单直投；wave2 SMTP 发送；
                 验证码分级处理；结果 → run_log
                 ↓
⑦ 反馈           日报（内部）+ 客户报告（过滤版）；异常标记
                 ↓
⑧ 复盘           上线率/失败率复盘 → 调整配额、模板、排除清单 → 回到 ④

步骤归属：①② 人工（销售/运营），③④⑤⑥⑦ 系统执行（仅 ④ 一道人工闸），⑧ 人工基于系统数据做策略。

5. 模拟暴露的设计缺口 → 设计备注

  1. 多客户发件身份：wave2 SMTP 凭据目前是单一全局 env 文件。三个客户各自用自己邮箱时，需要按项目的发件身份（姓名 + 邮箱 + 凭据路径写进 projects/<domain>.yaml）。未指定时默认用共享运营邮箱。
  2. 客户报告收件人：项目 YAML 里的 report.email（按项目），回落到全局配置——现有配置模型已兼容。
  3. 客户 A 二期不需要改 schema：只是 page 资产里加新条目；匹配把新条目当高优落地 URL（Phase 3 打分时给新条目加新鲜度加权——待确认）。
  4. 客户邮箱角色模型（真实用法确认）：客户邮箱承担两种业务角色——
  5. 注册角色：目录/表单提交的品牌身份（落到 contact-email 资产，供 wave1 表单、CUA 填充和 wave2 发件身份使用）；
  6. 汇总角色：阶段性数据摘要的收件方（客户报告 / 日报，report.email）。 一个邮箱可以同时承担两种角色（当前 azgames 实践：一个 Gmail 既做注册又收日报）。配置模型天然支持——同一地址可同时出现在 contact-email 和 report.email；将来拆成两个邮箱只是改配置，不动 schema。客户邮箱属用户数据：凭据只放 gitignored env 文件，地址不入仓库。

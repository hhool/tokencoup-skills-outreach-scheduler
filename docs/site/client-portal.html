Client portal — auth & dashboard design

Client portal — auth & dashboard design

Scope: the client-facing web surface for the commercialization track. Clients register/login with email (incl. Google / Facebook OAuth), then read two things and nothing else: quota consumption (what their package bought, what it has consumed) and promotion effect (what the service produced). The portal is read-only over the same database the scheduler writes; it never bypasses a human gate and never exposes internal machinery (pool, templates, sender credentials).

1. Identity & access model

item decision
registration email + verification mail (reuses B3 IMAP machinery)
OAuth Google and Facebook sign-in buttons; OAuth identity binds to the same client record on first login
one identity one client record per contract; multiple viewers per client are a later phase
mapping client record ↔ one or more projects (matches client-intake §2)
roles client (read-only own data); ops (internal, existing CLI access)
hosting extends the fly.io app (HTTP side); portal API reads sqlite read-only

Anti-goal: the portal is not a self-service submission tool. Clients never trigger deliveries; they read ledgers and approve queue items that the human gate already confirmed.

1.5 Self-service project creation + trial credits (ratified 2026-11-18)

Registered users may create their own promotion project and receive trial credits — this is the acquisition funnel for the 2B service.

Flow

  1. Create project — wizard collects: target domain, site title, site summary, contact email (the same §5a asset schema the scheduler already ingests), market/tags. One project per verified domain.
  2. Verify ownership — DNS TXT record or HTML meta tag on the domain (same convention as search-console verification). No verification → no project activation, no trial. This is the anti-abuse anchor: one trial per verified domain, not per email (otherwise throwaway mailboxes farm trials).
  3. Trial grant — on activation the project receives trial credits (default: 3 live links, one-time, quota_type=trial). Consumption uses the same View A ledger; a trial link that never reaches live is not billed and does not consume trial quota.
  4. Conversion path — when trial credits are consumed or exhausted, View A switches to a "choose a package" state; purchased packages become quota_type=paid credits. Historical trial ledger stays visible as the evidence the prospect evaluates.

Write-path discipline

  • The portal's only direct writes are: client identity records, project creation requests, ownership-verification markers, package purchase records. All delivery-side tables (pool, match, plan, link_verify) remain scheduler-owned.
  • A created project enters the normal pipeline: probe → match → human confirm → schedule → execute. Self-service changes nothing about who pulls the trigger on submissions.
  • Trial projects are tagged so B5 ops view and R-522 rhythm treat them under the same domain-level quotas as paying clients (no free tier that starves paid delivery capacity).

Trial parameters (defaults, tunable per config)

parameter default rationale
trial credits 3 live links one directory-spread sample, enough to show ledger + effect views
trial window 14 days forces the pacing conversation early
trial per domain 1 ownership-verified domain is the identity
trial per OAuth identity 1 blocks same-person multi-domain farming

Anti-abuse guards (delivered 2026-11-18)

Implemented in src/osched/guard.py; every grant lands in trial_ledger (email_canon, reg_domain, ip) so the same signal cannot mint a second trial.

vector guard
throwaway mailboxes / aliases canonical_email() — +tag stripped, gmail dots stripped, googlemail≡gmail; one trial per canonical mailbox
site split into sub-domains registrable_domain() (eTLD+1) — shop.a.com collides with a.com for both the ledger and the "already claimed" check
second account on the same laptop / office client_ip() reads Fly-Client-IP/CF-Connecting-IP; one trial per IP, and 5 signups per IP per 24h
draft hoarding max 5 unverified project_request rows per account

Refusal is graceful: the project activates with quota_total=0, quota_type=paid, and trial_note carrying the reason (email_reused / site_reused / site_claimed / ip_reused / client_used). The SPA dashboard prints the reason with a package CTA; the admin console shows it per project and can set quota manually. Manual "approve" runs the mailbox/site checks and skips only the network rule, since the approval IP belongs to the operator.

Credits are enforced, not just displayed: guard.credit_cap / allowance bound both scheduler.generate_plan (won't schedule beyond remaining credits) and scheduler.due_today (won't execute beyond them); verify.check_one mirrors each live transition into project_request.quota_used. Projects without a portal request stay uncapped (our own sites, imports), and so does any request marked quota_type='internal' — the escape hatch for operator-owned sites that should never be throttled by a customer-facing credit count.

Tests: PYTHONPATH=src python3 -m pytest tests/test_guard.py -q (24 cases: normalisation, verdict matrix, schedule/execute ceilings).

2. View A — quota consumption (额度消耗)

Two layers: package credits (commercial) and delivery capacity (operational transparency).

2.1 Package credits (commercial layer)

Per the ratified pricing verdict (business.md §Pricing), 2B service is sold per delivered live link, packaged as a monthly credit allowance.

  • quota_total = package size (e.g. 30 live links / month)
  • quota_used = links confirmed live in the current billing period
  • consumption rule: only live consumes credits. submitted/sent are work-in-progress, never billed; a link that never reaches live after auto-retry + human fallback is not billed (service guarantee).
  • data source: link_verify (verdict=live) joined to plan/match → project → client.

2.2 Delivery capacity (operational layer)

Why the client sees pacing: quotas are per-domain and shared by platform rules, so submissions are deliberately staggered over days (R-522/R-530).

  • per-domain address budget: 100 / domain / 24h — rendered as a capacity gauge per target domain, "used today" vs "budget".
  • client daily rhythm: scheduled vs delivered counts over the rolling window; SLA row (project sla.min_daily) with on/off-track badge — reuses B5 ops.py alerts, filtered to the viewer's projects.
  • wave composition: which items are waiting (wave1 one-shot vs wave2 multi-touch) so delays are legible as pacing, not stall.

3. View B — promotion effect (推广效果)

Four tiers, ordered by evidence strength. Tier 1–3 ship with portal v1; Tier 4 is a later phase (needs UTM/GSC integration).

Tier 1 — live-link ledger (hard evidence)

Every live link as a row: target URL, anchor, placement domain, DR, confirmed date, verify verdict history. This is the invoice-grade evidence: each row is a consumed credit with a receipt (link_verify timestamp). Filters: period, domain, DR band. Each receipt is a public, signed page (osched evidence-url <plan>) the client can open without logging in: listing URL, anchor, rel, first-live time, the last 12 checks with page hashes, and the captured listing screenshot (osched evidence-shot <plan> shot.png).

Tier 2 — placement quality

  • DR distribution of live placements (buckets: <30 / 30–60 / 60+)
  • source class mix (directory / blog / listing / answer) — from pool classification
  • captcha tier of source (none / v2 / v3) as a durability proxy: sources that guard submissions tend to guard deletion too.

Tier 3 — funnel trend

Weekly series: pending → confirmed → submitted/sent → live, plus live rate (live ÷ submitted) and approval rate (approved ÷ attempted). Data source: run_log + link_verify aggregation — same aggregation as B4 profile, projected to the client as trend charts.

Tier 4 — downstream traffic (later phase)

Referral visits from live placements via UTM-tagged links and GSC data for the served site. Out of portal v1: it requires touching the served sites' analytics, a separate integration.

6. Deployment topology (ratified 2026-11-18)

Frontend on Cloudflare Pages, backend on fly.io.

  • frontend/ root is the LinkAttest marketing landing page (index.html + landing.css, pure CSS, no JS): hero with a live-link ledger mockup, stats strip, how-it-works, differentiators, the ratified pricing tiers, FAQ. Portal CTAs link into /app/.
  • The client portal SPA lives at frontend/app/ (index.html + app.js + styles.css, vanilla JS, hash routing, routes #/login #/dashboard #/reports #/new #/admin #/pricing). Deployed via wrangler pages deploy frontend --project-name osched-portal.
  • #/pricing (public): the ratified per-live-link tiers + service guarantee, auth-aware CTA. Dashboard v2 adds a next-steps card (draft → verify button, verified → awaiting approval, rejected) and quota progress bars with a trial countdown (project_request.trial_until, set to +14d at trial activation; additive migration).
  • The SPA calls the fly backend's JSON API (/api/*) cross-origin with a bearer token in the X-Auth-Token header (localStorage). The API answers with permissive CORS (Access-Control-Allow-Origin: *) — auth is the token, not cookies, so wildcard origin is safe here.
  • The fly app keeps serving the legacy HTML pages on the same routes as a fallback; both UIs share the same API and database.
  • API_BASE in frontend/app/app.js is the single touch point when the backend moves to a custom domain.
  • Super-admin bootstrap: PORTAL_ADMIN_EMAILS (fly env) seeds the admin_whitelist at boot; whitelist members get role=admin at registration/login. Admin UI: approve requests, set quotas, manage the whitelist (last-admin removal is guarded).

Multilingual (EN / ZH, shipped 2026-11-18)

Two different mechanisms, deliberately:

surface mechanism URLs
marketing (landing, privacy) separate static pages per language — crawlable, each with its own canonical + hreflang cluster / (en), /zh/ (zh-Hans), /privacy, /zh/privacy
portal SPA client-side dictionary in frontend/app/app.js (DICT.en / DICT.zh + t()), no reload /app/#/…

Rules:

  • Static pages always carry the four-link hreflang set (en, zh-Hans, x-default → EN) and a visible switcher in the header (EN page → 中文, ZH page → EN). Adding a language = new directory (frontend/<lang>/) + hreflang entries in every existing page.
  • SPA language is persisted under portal_lang; default is navigator.language (zh* → Chinese, else English). The switcher is the last item in the portal nav; toggleLang() re-renders without reload.
  • Never hard-code UI copy in the SPA render functions — add a key to both DICT.en and DICT.zh and call t("key"). A missing key falls back to EN, so a missed translation degrades gracefully rather than breaking the page.
  • Values returned by the backend (API messages, report text) stay English; the SPA localises labels and chrome only.

Public contact address (required for the privacy policy)

frontend/privacy.html names a contact address for data requests, and the policy is only honest if that mailbox is read by a human. It must not be a personal mailbox (that address lands in every page's HTML, in git history, and in scraped copies).

Ratified: privacy@linkattest.com, delivered by Cloudflare Email Routing (available on the same zone, free, no extra MX provider).

Configured via API, not the dashboard — tools/setup_email_routing.py applies the whole thing (3 MX + SPF + DMARC + the routing rule) and is idempotent, so re-running it is safe:

CF_TOKEN=... CF_ZONE_ID=... CF_ZONE_NAME=linkattest.com \
CF_DESTINATION=<your verified mailbox> \
python3 tools/setup_email_routing.py --dry-run

State of the live zone (checked 2026-11-20)

item state
MX ×3 (route1/2/3.mx.cloudflare.net) present, no duplicates
SPF TXT (include:_spf.mx.cloudflare.net ~all) present
DMARC TXT (p=none) present
rule privacy@linkattest.com → operator mailbox present, enabled, literal matcher
forward target verified — Cloudflare accepted a rule targeting it
external mail to privacy@linkattest.com accepted by Cloudflare's MX
DKIM (cf2024-1._domainkey) published — RSA-2048, verified on the public DNS

Two read-only commands re-check all of that without writing anything:

python3 tools/setup_email_routing.py --check          # audit DNS + rule
python3 tools/setup_email_routing.py --probe-destination  # is the target verified?

--probe-destination works because Cloudflare refuses to create a rule whose forward target is not a verified destination (error 2054) and accepts the rule when the address is verified. The script creates a throwaway rule and deletes it again; two probe addresses came back 2054 while the operator's mailbox came back accepted, which is how the "destination must be verified" caveat below turned out to be already satisfied.

Two consequences of the blocked endpoints:

  1. The DKIM record had to come from the dashboard. CF generates cf2024-1._domainkey.<zone> when Email Routing is enabled, and the endpoint that returns it is blocked for this token. Enabling Email Routing once in the dashboard (Compute > Email Service > Email Routing

    linkattest.com) published the record; the public DNS now serves a valid RSA-2048 key, so forwarded mail carries a signature that passes instead of only an SPF pass. --publish-dkim writes the same record when the endpoint is reachable, for zones that are set up without the dashboard. The DMARC record stays p=none, so a forwarded email that fails DKIM does not also fail a strict DMARC policy and get filtered.

  2. The destination must already be verified. Destination addresses are account-level and this token cannot list or create them. Until the mailbox confirms the Cloudflare verification email, CF keeps the rule inactive and drops the mail — the API still reports enabled=true, so do not trust that field alone. --probe-destination is the check for it.

Also worth knowing: PATCH on a rule id is rejected with "Authentication error" by the same token that may POST and PUT rules. The script uses PUT for updates and never PATCH.

The forwarding destination is the operator's existing mailbox — CF requires the destination to confirm before it forwards, so the personal address stays private while privacy@ stays public.

If the address ever changes, it is a one-line edit in each of frontend/privacy.html and frontend/zh/privacy.html — never a policy rewrite. Because it is a plain string in two static pages, there is no config indirection worth adding for it.

客户端门户 — 注册登录与看板设计

范围：商业化轨道的客户端 Web 门面。客户用邮箱注册/登录（含 Google / Facebook OAuth），然后只看两样东西：额度消耗（套餐买了 什么、消耗了什么）和推广效果（服务产出了什么）。门户对调度器 写入的同一个数据库只读；不绕任何人工闸，也不暴露内部机制（池子、 模板、发件凭据）。

1. 身份与访问模型

项 决策

1.5 自助建项目 + 试用额度（2026-11-18 定稿）

注册用户可以自建推广项目并获得试用额度——这是 2B 服务的获客漏斗。

流程

  1. 建项目——向导收集：目标域名、站点标题、站点摘要、联系邮箱 （与调度器已接入的 §5a 资产 schema 相同）、市场/标签。每个已验证 域名一个项目。
  2. 验证归属——DNS TXT 记录或站点 HTML meta 标签（与搜索控制台 验证同一约定）。不验证 → 不激活、不给试用。这是防滥用锚点：试用 按已验证域名限量一次，不按邮箱（否则一次性邮箱能刷试用）。
  3. 发放试用——激活后项目获得试用额度（默认 3 条实链，一次性， quota_type=trial）。消耗走同一个 View A 台账；始终没到 live 的 试用链不计费、不占试用额度。
  4. 转化路径——试用额度用完或到期，View A 切到「选套餐」状态； 购买的套餐转为 quota_type=paid 额度。历史试用台账保持可见， 作为潜在客户评估时的证据。

写入路径纪律

  • 门户唯一允许的直接写入：客户身份记录、建项目请求、归属验证 标记、套餐购买记录。所有投递侧表（pool、match、plan、link_verify） 仍归调度器所有。
  • 新建项目进入正常管线：probe → match → 人工 confirm → schedule → execute。自助化不改变「谁扣动投递扳机」。
  • 试用项目打标，让 B5 运营视图和 R-522 节奏把它们与付费客户放在 同一域名级配额下（不允许饿死付费产能的免费层）。

参数 默认 理由
试用额度 3 条实链 覆盖多个目录的一次样本，足以展示台账+效果两个视图

试用防刷（2026-11-18 已交付）

2. 视图 A — 额度消耗

两层：套餐额度（商业层）与投递产能（运营透明层）。

2.1 套餐额度（商业层）

按已定稿定价裁决（business.md §Pricing），2B 服务按交付实链计价、 打包为月度额度。

  • quota_total = 套餐大小（如 30 条实链/月）
  • quota_used = 当前账期内确认 live 的链接数
  • 消耗规则：只有 live 消耗额度。submitted/sent 是在途工作， 永不计费；自动重投 + 人工兜底后仍未上线的链接不计费（服务 保障）。
  • 数据源：link_verify（verdict=live）连接 plan/match → project → client。

2.2 投递产能（运营层）

多语言（中英，2026-11-18 上线）

两种机制，刻意的分工：

面 机制 URL
营销页（落地页、隐私页） 每语言独立静态页——可被抓取，各自带 canonical + hreflang 组 /（en）、/zh/（zh-Hans）、/privacy、/zh/privacy

规则：

  • 静态页必须带四行 hreflang（en、zh-Hans、x-default → EN）， 头部有可见切换入口（英文页 → 中文，中文页 → EN）。加语言 = 新建目录（frontend/<lang>/）+ 在既有每页补 hreflang。

  • SPA 渲染函数里不许硬编码文案——在 DICT.en 与 DICT.zh 同时加 键并调 t("key")。缺键回退英文，漏翻只会降级不会坏页面。

线上区域现状（2026-11-20 实测）

项 状态

SPF TXT（include:_spf.mx.cloudflare.net ~all） 已在
DMARC TXT（p=none） 已在
规则 privacy@linkattest.com → 运维邮箱 已在、已启用、literal 匹配
转发目标地址 已验证——CF 接受了指向它的规则
外部发往 privacy@linkattest.com 的邮件 CF 的 MX 已接收
DKIM（cf2024-1._domainkey） 已发布——RSA-2048，公网 DNS 已核对

两条只读命令可以随时复查上面每一项，不写任何东西：

python3 tools/setup_email_routing.py --check             # 审计 DNS + 规则
python3 tools/setup_email_routing.py --probe-destination # 目标地址验证了吗

--probe-destination 能用，是因为 CF 会拒绝创建"目标地址未验证"的规则 （错误码 2054），而地址已验证时它会接受。脚本建一条临时规则、验完立刻 删掉：两个探测地址都回了 2054，运维邮箱被接受——下面"目标地址必须验证过" 那条警告因此已经确认不成立。

被拒端点带来两个后果：

  1. DKIM 记录只能从面板拿到。 CF 在启用 Email Routing 时生成 cf2024-1._domainkey.<zone>，而返回它的端点对本 token 是被拒的。在面板 里启用一次 Email Routing（Compute > Email Service > Email Routing > linkattest.com）之后，记录就发布了：公网 DNS 现在能查到一把合法的 RSA-2048 公钥，转发邮件带的是能过校验的签名，而不只是 SPF 兜底。 --publish-dkim 会在端点可读时写同一条记录，给那些不走面板搭出来的 区域用。DMARC 仍是 p=none：这样"DKIM 失败"不会连带"DMARC 严格策略 失败"，不会被拦进垃圾箱。
  2. 目标地址必须事先验证过。 目标地址是账户级的，本 token 既不能列 也不能建。在收件邮箱点掉 CF 的验证邮件之前，CF 会让规则保持未激活并 丢弃邮件——而 API 仍然返回 enabled=true，所以不要单独相信这个字段。 --probe-destination 就是查这件事的命令。

另一个坑：对规则 id 做 PATCH 会被同一个 token 以 "Authentication error" 拒绝，尽管它可以 POST 和 PUT 规则。脚本的更新路径一律用 PUT，不用 PATCH。

转发目标填运维自己的邮箱——CF 要求目标地址先确认才转发，所以个人地址保持 私密，privacy@ 保持公开。

地址若变更，改 frontend/privacy.html 与 frontend/zh/privacy.html 各一行即可，不动政策正文。它只是两个静态页里的字符串，不值得为此加配置 间接层。

Business layer — commercialization roadmap

Business layer — commercialization roadmap

Positioning: the business layer is the commercialization track. The functional layer (import → probe → match → execute → report) is the machine; the business layer is what turns the machine into a client service that can be sold, delivered and renewed. Every item below either produces client-visible deliverables (B1/B2), extends deliverable service capacity (B3/B4), enables scaling to more clients (B5), or secures the supply that the service resells (B6).

Derived from the shipped functional layer. This doc records the ratified discussion: which business features build on that layer, in what order, and why. No functional-layer rework is implied.

Commercialization mapping

commercialization question answers
客户凭什么付费？ What does the client pay for? B1 live-link ledger + B2 client report
服务能力边界在哪？ What can we deliver? B3 account lifecycle + B4 submittability
规模化靠什么？ How does it scale? B5 multi-client ops view
货源谁保障？ Who secures supply? B6 competitor refresh

Priority order: 1 → 2 → 3 first (proof-of-value closed loop), then 4/5 (efficiency), 6 (supply).

B1. Live-link verification ledger (priority 1)

Submission ≠ live link. After a plan reaches submitted/sent, re-visit the directory page after N days and confirm the client's link actually appears; produce a deliverable "live links list". Misses auto-retry or fall to the human queue.

  • Built on: plan state machine (new live state after submitted) + probe re-visit machinery (probe_cache already has the 30-day audit framework) + the CUA channel can reuse the same browser run.
  • Value: the only hard evidence a client pays for; without it the daily report's "submitted" is a process metric, not a result metric.

B2. Client report (priority 2)

A client-facing filtered view of run_log: submissions, success rate, live-link list, items awaiting the client's decision. Emailed to the client summary mailbox on a weekly/monthly digest.

  • Built on: report.py five-section skeleton + filter/render layer + report.email (client summary-role mailbox).
  • Value: the retention/renewal communication artifact; implements the "client report" row in client-intake §3.

B3. Directory account lifecycle (priority 3)

Many directories require a registered account before submission. Close the loop on the registration-role mailbox: fetch verification mails (IMAP), activate accounts, keep a credential ledger, reuse aged accounts.

  • Built on: contact-email asset (registration role) + the SMTP/IMAP credential model (email_code_imap is already reserved in config).
  • Value: unlocks the large "register-first" directory segment; accounts become reusable assets.

B4. Submittability profile & template attribution (priority 4)

Aggregate execution failures (bot-blocked / captcha / no-form / 4xx) into a per-domain submittability profile feeding min_score and exclusion lists; rotate wave2 templates and attribute by approval rate.

  • Built on: run_log already records every failure detail — this is an aggregation layer only.
  • Value: quota is finite (100 addresses/domain/day); spend it where forms actually pass.

B5. Multi-client operations view (priority 5)

Per-client aggregation table: pending / confirmed / submitted / live / human-queue, plus a client-level SLA (minimum daily submissions) with alerts on shortfall.

  • Built on: project + plan tables; a pure query layer.
  • Value: surfaced by the three simulated clients; the operations base before scaling beyond a handful of clients.

B6. Competitor-driven supply refresh (priority 6)

Upgrade WDC competitor harvesting from manual import to a scheduled refresh: new directories flow into the pool → probe → match → confirmation queue automatically; humans only confirm.

  • Built on: import chain + cron pipeline segment already reserves a slot.
  • Value: keeps backlink supply from going dry.

Ratified mailbox-role context (client-intake §5.4)

The client mailbox carries two roles — registration (contact-email asset) and periodic summary (report.email) — and one mailbox may serve both. B2's recipient is the summary role; B3's credentials are the registration role. Splitting into two mailboxes later is config-only.

Strategy context (ratified 2026-11-18)

  • Why this exists: the served sites must pass AdSense review and grow on their own traffic; backlinks are the traffic engine behind that goal. Every commercial-layer feature traces back to "more real links, proven to the client".
  • Operations mode: backend runs on fly.io (HTTP-side pipeline, cron, sqlite volume) — fully agent-free (no assistant-platform dependency). CUA (real-Chrome captcha) stays on the desktop for the current sites and is acceptable in early commercial stage; later replace with an open-source or commercial captcha solution (single touch point: §7.1 routing). See docs/deployment.md for the duty matrix.
  • AI layer (later phase): the backend will add AI for client requirement/case matching, planning, and capability matching. AI plugs into the existing CLI/DB contracts as a caller, never bypassing human gates. Hook-point table in docs/deployment.md.

Competitor landscape & market verdict (ratified 2026-11-18)

Scope: 2C/2B × overseas/domestic. Findings from a structured sweep of the existing link-building tool market, distilled into judgments that constrain pricing, packaging and the captcha-replacement plan.

Market matrix

quadrant incumbent examples what they sell verdict for us
overseas 2C tools open-source scrapers/submitters, browser-automation frameworks free self-serve tooling do NOT compete — free/open-source saturates the low end at $0
overseas 2B SaaS Respona, Pitchbox-style outreach platforms per-link pricing roughly $100–500/link, campaign management benchmark only; our differentiation is the live-link closed loop (submission → re-visit → verified live), which none of them productizes
overseas 2B done-for-you link-building agencies per-link deliverables, manual QA direct comparables for pricing our service tier
domestic 2C none in this category — no directory-link category exists
domestic 2B 友链 exchange ecosystems (platforms + manual trades) friend-link placement, not directory submission different category; not a competitor, a supply channel option

Judgments

  1. No 2C tool-selling. The open-source tier already prices at zero; a paid 2C tool has no wedge. Tooling stays internal.
  2. Sell 2B service, priced against Resona-class SaaS. The market anchor is ~$100–500 per delivered link. Our edge is evidence: the live-link ledger (B1) plus the client report (B2) prove the link exists — no competitor in the sweep closes that loop automatically.
  3. CUA replacement candidate: open-source real-Chrome engines. The ratified desktop-only captcha phase has a named successor candidate — an open-source, MCP-exposed real-Chrome automation engine (the class of engine behind commercial "AI browser operator" products). Interface is compatible with the §7.1 routing touch point; swap is config-level. Re-evaluate when commercial volume justifies it.
  4. The pool is a durable asset. ~55k directory pool + probe_cache verdict history compounds with every run; it is the moat a new entrant cannot copy by installing a tool.
  5. Domestic market: no directory category. Domestic demand is served by the 友链 ecosystem instead. Treat domestic as a possible supply or resale channel, not a product market.

Pricing implication (draft)

Anchor 2B service pricing to the delivered-link unit, not subscription: per-live-link pricing at a discount to the $100–500/link SaaS ceiling, with the live-link ledger as the receipt that justifies the invoice.

业务层 — 商业化落地路线图

业务层 — 商业化落地路线图

定位：业务层就是商业化落地轨道。 功能层（import → probe → match → execute → report）是「机器」；业务层是把机器变成可售卖、可交付、可续费 的客户服务。下面每一项要么产出客户可见的交付物（B1/B2），要么扩展可交付 的服务能力（B3/B4），要么支撑规模化接更多客户（B5），要么保障服务的货源 （B6）。

基于已交付的功能层。本文档记录已讨论定稿的业务层功能：各自建立在哪些 现有模块之上、顺序与理由。不涉及功能层返工。

商业化对应关系

商业化问题 回答
客户凭什么付费？ B1 实链台账 + B2 客户报告
服务能力边界在哪？ B3 账号生命周期 + B4 可投递性画像
规模化靠什么？ B5 多客户运营视图
货源谁保障？ B6 竞品供给刷新

优先级：1 → 2 → 3 先做（价值证明闭环），4/5 效率层，6 供给层。

B1. 实链确认台账（优先级 1）

提交成功 ≠ 链接上线。 计划到达 submitted/sent 后，N 天后自动回访 该目录页，确认客户链接真实出现；产出可交付的「已上线链接清单」。未出现的 自动重投或进人工队列。

  • 建立在：plan 状态机（submitted 后新增 live 状态）+ probe 回访机制 （probe_cache 已有 30 天审计框架）+ CUA 通道可复用同一次浏览器会话。
  • 价值：客户付费的唯一硬证据；没有它，日报里的 submitted 只是过程指标。

B2. 客户报告（优先级 2）

面向客户的 run_log 过滤视图：提交数、成功率、实链清单、待客户决策项。 按周/月摘要直发客户汇总邮箱。

  • 建立在：report.py 五段式骨架 + 过滤/渲染层 + report.email（客户邮箱的 汇总角色）。
  • 价值：续费沟通载体；落地 client-intake §3 的「客户报告」条目。

B3. 目录账号生命周期（优先级 3）

大量目录要求先注册账号才能提交。把注册角色邮箱的链路闭合：自动收验证信 （IMAP）、激活账号、凭据台账、老账号复用换量。

  • 建立在：contact-email 资产（注册角色）+ SMTP/IMAP 凭据模型 （config 里 email_code_imap 已预留）。
  • 价值：解锁大批「需注册」目录；账号成为可复用资产。

B4. 可投递性画像与模板归因（优先级 4）

把执行失败原因聚合（bot-blocked / captcha / 无表单 / 4xx）成每域名 「可投递性画像」，反哺 min_score 和排除清单；wave2 多模板轮换按通过率 归因。

  • 建立在：run_log 已记录全部失败明细——纯聚合层。
  • 价值：配额有限（域名 100 地址/天），把额度花在能通过的站点上。

B5. 多客户运营视图（优先级 5）

按客户聚合总表：pending / confirmed / 已提交 / 实链 / 人工待办，加客户级 SLA（每日最低提交数）与不达标预警。

  • 建立在：project + plan 表；纯查询层。
  • 价值：三个模拟客户已暴露的需求；规模化前的运营底座。

B6. 竞品驱动的供给刷新（优先级 6）

WDC 竞品收割从手动导入升级为定时刷新：新目录自动入池 → probe → match → 待确认队列，人只做 confirm。

  • 建立在：import 链路 + cron pipeline 段已留位。
  • 价值：外链供给不断档。

邮箱角色模型背景（client-intake §5.4 已定稿）

客户邮箱承担两种角色——注册（contact-email 资产）与阶段性汇总 （report.email），一个邮箱可同时兼任。B2 的收件人是汇总角色，B3 的凭据 是注册角色。将来拆成两个邮箱只改配置。

战略背景（2026-11-18 拍板）

  • 为什么做这个：服务的站点要过 AdSense 审核、靠自身流量增长；外链 是这一目标的流量引擎。商业层每个功能都回溯到「更多真实链接，向客户 证明」。
  • 运营形态：后台跑 fly.io（HTTP 侧 pipeline + cron + sqlite 卷）， 完全脱离智能体平台运行（任何环节无平台依赖）。CUA（真 Chrome 验证 码）前期留在本地服务现有站点、商业初期可接受；后期替换为开源或商用 验证码方案（唯一接触点 §7.1 路由）。职责矩阵见 docs/deployment.zh.md。
  • AI 层（后期）：后台将加入 AI 用于客户需求/案例对接、策划、能力 对接。AI 只作为现有 CLI/DB 契约的调用方，不绕过人工闸。挂接点表见 docs/deployment.zh.md。

竞品格局与市场裁决（2026-11-18 定稿）

范围：2C/2B × 海外/国内。对外链工具市场做了结构化扫描，结论收敛为 对定价、打包与验证码替换计划有约束力的判断。

市场矩阵

象限 现有玩家 卖什么 我们的裁决
海外 2C 工具 开源采集/提交器、浏览器自动化框架 免费自助工具 不做——免费/开源已把低端打到 $0
海外 2B SaaS Respona、Pitchbox 类外联平台 按 link 计费约 $100–500，加活动管理 只做定价锚；我们的差异点是实链闭环（提交→回访→验证上线），扫描范围内没有竞品把它产品化
海外 2B 代做 外链代发服务商 按 link 交付，人工质检 我们服务档位的直接定价参照
国内 2C 该品类不存在 — 无目录外链品类
国内 2B 友链交换生态（平台+人工换链） 友链位，不是目录提交 不同品类；不是竞品，是可选供给渠道

判断

  1. 不做 2C 工具。 开源层已是零价，付费 2C 工具没有楔子。工具只留 内部自用。
  2. 卖 2B 服务，对标 Resona 级 SaaS 定价。 市场锚点约 $100–500/实链。 我们的筹码是证据：实链台账（B1）+ 客户报告（B2）能证明链接存在—— 扫描范围内没有竞品自动闭合这个环。
  3. CUA 替换候选：开源真 Chrome 引擎。 已定稿的「验证码留桌面」阶段 有具名继任者——开源、以 MCP 接口暴露的真 Chrome 自动化引擎（即商业 「AI 浏览器操作员」产品背后的那一类引擎）。接口与 §7.1 路由接触点 兼容，替换是配置级改动。商业量起来后再评估切换。
  4. 池子是长期资产。 ~55k 目录池 + probe_cache 判定史随每次运行 复利增长；这是新进入者装个工具抄不走的护城河。
  5. 国内市场：无目录品类。 国内需求由友链生态承接。把国内当作可能的 供给或转售渠道，而不是产品市场。

定价含义（草案）

2B 服务按交付实链计价，不做订阅：以低于 $100–500/link SaaS 天花板一定 折扣的每实链价格收费，实链台账就是支撑开票的凭证。

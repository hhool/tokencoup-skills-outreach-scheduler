Pool bridge — workbench ledger -> pool

A harvested pool (WDC-style crawls) is full of web-2.0 property roots: blogspot, wordpress.com, reddit, tumblr. Those need an account and a post, not a form POST, so they classify as submit_type=unknown and stall in the wave-3 human queue. The curated ledger the SEO workbench keeps per site (~/seo/<site>/targets.jsonl) already answers that question per target.

Bridge it one way:

python3 bin/osched.py import-workbench ~/seo/<site>/targets.jsonl [--min-fit 50]

Rules enforced by the importer (src/osched/workbench.py):

  • One way. The workbench stays the ledger of record (status, link_state, evidence). We read a snapshot; nothing writes back. Re-import is idempotent.
  • Dedupe by pay-level domain. An existing pool row for the domain is upgraded in place; its submit_url becomes entry_url only when the row has none (a specific endpoint is never replaced by a root URL).
  • No downgrades. A ledger row with submit_type=unknown never overwrites a probed/curated type — that would push the plan back to wave 3 for nothing.
  • dropped targets are skipped. working / pending / done are kept.
  • Curated rows carry fit_score in hints_json; matching treats it as the evidence prior and lets the row into the pending queue without clearing min_score (scoring.curated_trust: true, default). The human confirm gate still stands between the queue and delivery.

Execution gates (why a due plan goes to human)

gate rule why
wave-3 submit_type=unknown never auto-executes nobody knows how to submit; a blind POST to a random page is worse than no attempt
email channel=email is manual unless delivery: {email_auto: true} R-520: outreach mail is human-sent
form live page must expose a form with a URL-ish field login / signup / search / newsletter boxes are not submission forms
captcha browser-class captcha -> cua; unknown -> human §7.1 tiers; a stale cached captcha never routes a formless page to a browser

Live-link alerts (evidence layer)

Every verify pass also runs edge detection over the check series and emails the ops mailbox (cfg.report.email) — never the client directly; clients see drops via the weekly report and the receipt page.

alert fires when dedupe
link-drop a previously-live link rechecks as missing/unreachable edge only — consecutive missings are quiet
rel-change the rel attribute of a live link changed between checks per change
live-check-exhausted missings after the first live verdict hit MAX_ATTEMPTS -> human once, at handoff

Fail-open: a mail failure logs run_log action='alert' result='failed' and never breaks the verify loop. Receipt URL is attached when available. Live plans recheck every RECHECK_AFTER_DAYS (14) days.

Cron entry points

scripts/daily.sh is the only cron entry. Two segments:

segment what it does cadence
run execute every active project (due plans only) + report daily, at scheduler.run_at (default 09:30)
pipeline import -> probe -> classify -> dr -> match -> schedule weekly, or after new source data lands
client-report (CLI, not a daily.sh segment) per-project client-facing report (B2): live-link list, activity, decisions weekly (--days 7) or monthly (--days 30)

Weekly client report via cron:

0 10 * * 1 /path/to/outreach-scheduler/bin/osched.py client-report <project-domain> --days 7 >> /tmp/osched.cron.log 2>&1

Install (crontab -e):

30 9 * * * /path/to/outreach-scheduler/scripts/daily.sh run >> /tmp/osched.cron.log 2>&1
0 9 * * 1 /path/to/outreach-scheduler/scripts/daily.sh pipeline >> /tmp/osched.cron.log 2>&1

Rules: - Every stage is idempotent; a cron re-run never double-submits (plan rows leave queued once executed). - dr is fail-open: an unbound/absent API key skips enrichment, never blocks the pipeline. - Failures never crash the chain (|| true per project); everything lands in run_log and shows up in the daily report's human-action section.

DR (Open PageRank) IP binding

The free key is bound to one IP address. If the API returns 403 This free API key is set to another IP address, either update the allowed IP at keywordseverywhere.com/account/openpagerank, or run the dr stage on the machine whose IP matches the binding. A stable server IP is preferable for batch enrichment (55k+ domains run against a 30k/month budget); a laptop on mobile broadband changes IPs and will need rebinding.

State machine quick reference

plan.state meaning
queued scheduled, awaiting execution
submitted / sent wave1 / wave2 done
live verified live link on the directory page (B1 ledger)
cua needs the CUA browser channel (captcha class)
human needs a human (bot-blocked, no email, unknown captcha, 4xx)
failed retryable failure exhausted (5xx/network, max 3)

Pool 桥接 —— workbench 台账 → pool

爬取来的 pool（WDC 类）里大量是web2.0 平台根域名：blogspot、 wordpress.com、reddit、tumblr。这些要「开户 + 发文」，不是表单直投， 所以一律归为 submit_type=unknown，卡在 wave3 人工队列。而 SEO 工作台 按站点维护的策展台账（~/seo/<site>/targets.jsonl）已经逐条回答了这个 问题。

单向桥接：

python3 bin/osched.py import-workbench ~/seo/<site>/targets.jsonl [--min-fit 50]

导入器（src/osched/workbench.py）强制以下规则：

  • 单向：workbench 仍是台账主（status / link_state / 证据都在那边）， 这里只读快照，永不回写；重复导入幂等。
  • 按可注册域去重：已有 pool 行就地升级；submit_url 只在 entry_url 为空时写入（具体端点绝不被根 URL 覆盖）。
  • 不允许降级：台账里 submit_type=unknown 的行不会覆盖已探测/已策展 的类型——那只会把计划无缘无故打回 wave3。
  • 跳过 dropped：保留 working / pending / done。
  • 策展行的 fit_score 存进 hints_json，匹配时当作证据先验，并允许 该行绕过 min_score 进待确认队列（scoring.curated_trust: true，默认开）。 人工 confirm 闸仍在队列与投递之间。

执行闸门（到期计划为何落 human）

闸门 规则 原因
wave3 submit_type=unknown 永不自动执行 还没人搞清「怎么投」；盲投到随机页比不投更糟
邮件 channel=email 默认人工，除非项目声明 delivery: {email_auto: true} R-520：外联邮件人工发送
表单 实时页面必须存在含 url 类字段的表单 登录/注册/搜索/订阅框不是提交表单
验证码 浏览器类 → cua；未知 → human §7.1 分级；缓存的旧验证码不会把无表单页面送进浏览器

实链告警（证据层）

每次验活同时对检查序列做边沿检测，命中即发运维信箱 （cfg.report.email）——不直发客户；客户通过周报与证据页感知掉链。

告警 触发 去重
link-drop 曾 live 的链接复检变 missing/unreachable 只在边沿触发——连续未命中保持安静
rel-change live 链接的 rel 属性在两次检查间变化 每次变化
live-check-exhausted 首次 live 后的 missing 达到 MAX_ATTEMPTS → 进人工 交接时一次

Fail-open：发信失败记 run_log action='alert' result='failed'，绝不中断 验活循环。可用时附证据页 URL。live 计划每 RECHECK_AFTER_DAYS（14） 天复检一轮。

Cron 入口

scripts/daily.sh 是唯一 cron 入口，两个段：

段 内容 频率
run 对所有 active 项目执行到期计划（execute）+ 日报（report） 每日，scheduler.run_at（默认 09:30）
pipeline import -> probe -> classify -> dr -> match -> schedule 供给链 每周一次，或新源数据到位后手动跑

安装（crontab -e）：

30 9 * * * /path/to/outreach-scheduler/scripts/daily.sh run >> /tmp/osched.cron.log 2>&1
0 9 * * 1 /path/to/outreach-scheduler/scripts/daily.sh pipeline >> /tmp/osched.cron.log 2>&1

规则： - 每个阶段幂等；cron 重跑不会重复投递（计划行一旦执行就离开 queued）。 - dr fail-open：key 未配置/未绑定时跳过富化，不阻塞流水线。 - 单项目失败不断链（每项目 || true）；全部落 run_log，出现在日报「人工待办」段。

DR（Open PageRank）IP 绑定

免费 key 绑定单一 IP。若 API 返回 403 This free API key is set to another IP address，二选一： 在 keywordseverywhere.com/account/openpagerank 改绑允许 IP，或在与绑定 IP 一致的机器上跑 dr 阶段。批量富化（55k+ 域名对 30k/月额度）建议放固定 服务器 IP；家宽/移动网络 IP 漂移，会反复需要改绑。

计划状态机速查

plan.state 含义
queued 已排期待执行
submitted / sent wave1 / wave2 完成
live 回访确认链接已上线（B1 实链台账）
cua 待 CUA 浏览器通道（验证码类）
human 需人工（bot-blocked、无邮箱、未知验证码、4xx）
failed 可重试失败耗尽（5xx/网络，最多 3 次）

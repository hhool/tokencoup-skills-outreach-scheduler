# 业务层 — 商业化落地路线图

**定位：业务层就是商业化落地轨道。** 功能层（import → probe → match →
execute → report）是「机器」；业务层是把机器变成可售卖、可交付、可续费
的客户服务。下面每一项要么产出客户可见的交付物（B1/B2），要么扩展可交付
的服务能力（B3/B4），要么支撑规模化接更多客户（B5），要么保障服务的货源
（B6）。

基于已交付的功能层。本文档记录已讨论定稿的业务层功能：各自建立在哪些
现有模块之上、顺序与理由。不涉及功能层返工。

英文版：business.md。

## 商业化对应关系

| 商业化问题 | 回答 |
|---------------------------|---------|
| 客户凭什么付费？ | B1 实链台账 + B2 客户报告 |
| 服务能力边界在哪？ | B3 账号生命周期 + B4 可投递性画像 |
| 规模化靠什么？ | B5 多客户运营视图 |
| 货源谁保障？ | B6 竞品供给刷新 |

## 优先级：1 → 2 → 3 先做（价值证明闭环），4/5 效率层，6 供给层。

---

## B1. 实链确认台账（优先级 1）

**提交成功 ≠ 链接上线。** 计划到达 `submitted`/`sent` 后，N 天后自动回访
该目录页，确认客户链接真实出现；产出可交付的「已上线链接清单」。未出现的
自动重投或进人工队列。

- 建立在：plan 状态机（`submitted` 后新增 `live` 状态）+ probe 回访机制
  （probe_cache 已有 30 天审计框架）+ CUA 通道可复用同一次浏览器会话。
- 价值：客户付费的唯一硬证据；没有它，日报里的 submitted 只是过程指标。

## B2. 客户报告（优先级 2）

面向客户的 run_log 过滤视图：提交数、成功率、**实链清单**、待客户决策项。
按周/月摘要直发客户汇总邮箱。

- 建立在：report.py 五段式骨架 + 过滤/渲染层 + report.email（客户邮箱的
  汇总角色）。
- 价值：续费沟通载体；落地 client-intake §3 的「客户报告」条目。

## B3. 目录账号生命周期（优先级 3）

大量目录要求先注册账号才能提交。把注册角色邮箱的链路闭合：自动收验证信
（IMAP）、激活账号、凭据台账、老账号复用换量。

- 建立在：contact-email 资产（注册角色）+ SMTP/IMAP 凭据模型
  （config 里 `email_code_imap` 已预留）。
- 价值：解锁大批「需注册」目录；账号成为可复用资产。

## B4. 可投递性画像与模板归因（优先级 4）

把执行失败原因聚合（bot-blocked / captcha / 无表单 / 4xx）成每域名
「可投递性画像」，反哺 min_score 和排除清单；wave2 多模板轮换按通过率
归因。

- 建立在：run_log 已记录全部失败明细——纯聚合层。
- 价值：配额有限（域名 100 地址/天），把额度花在能通过的站点上。

## B5. 多客户运营视图（优先级 5）

按客户聚合总表：pending / confirmed / 已提交 / 实链 / 人工待办，加客户级
SLA（每日最低提交数）与不达标预警。

- 建立在：project + plan 表；纯查询层。
- 价值：三个模拟客户已暴露的需求；规模化前的运营底座。

## B6. 竞品驱动的供给刷新（优先级 6）

WDC 竞品收割从手动导入升级为定时刷新：新目录自动入池 → probe → match →
待确认队列，人只做 confirm。

- 建立在：import 链路 + cron `pipeline` 段已留位。
- 价值：外链供给不断档。

---

## 邮箱角色模型背景（client-intake §5.4 已定稿）

客户邮箱承担两种角色——注册（contact-email 资产）与阶段性汇总
（report.email），一个邮箱可同时兼任。B2 的收件人是汇总角色，B3 的凭据
是注册角色。将来拆成两个邮箱只改配置。

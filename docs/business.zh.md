# 业务层 — 商业化落地路线图

**定位：业务层就是商业化落地轨道。** 功能层（import → probe → match →
execute → report）是「机器」；业务层是把机器变成可售卖、可交付、可续费
的客户服务。下面每一项要么产出客户可见的交付物（B1/B2），要么扩展可交付
的服务能力（B3/B4），要么支撑规模化接更多客户（B5），要么保障服务的货源
（B6）。

基于已交付的功能层。本文档记录已讨论定稿的业务层功能：各自建立在哪些
现有模块之上、顺序与理由。不涉及功能层返工。

英文版：business.md。

## 商业化对应关系

| 商业化问题 | 回答 |
|---------------------------|---------|
| 客户凭什么付费？ | B1 实链台账 + B2 客户报告 |
| 服务能力边界在哪？ | B3 账号生命周期 + B4 可投递性画像 |
| 规模化靠什么？ | B5 多客户运营视图 |
| 货源谁保障？ | B6 竞品供给刷新 |

## 优先级：1 → 2 → 3 先做（价值证明闭环），4/5 效率层，6 供给层。

## B1. 实链确认台账（优先级 1）

**提交成功 ≠ 链接上线。** 计划到达 `submitted`/`sent` 后，N 天后自动回访
该目录页，确认客户链接真实出现；产出可交付的「已上线链接清单」。未出现的
自动重投或进人工队列。

- 建立在：plan 状态机（`submitted` 后新增 `live` 状态）+ probe 回访机制
  （probe_cache 已有 30 天审计框架）+ CUA 通道可复用同一次浏览器会话。
- 价值：客户付费的唯一硬证据；没有它，日报里的 submitted 只是过程指标。

**证据层（2026-11-19 上线）。** 验活从「单次判定」升级为时间序列：

- `link_check` —— append-only 事件表（result、http、rel、锚文本、页面
  sha256、时间戳）。`link_verify` 保持「最新判定」摘要，门户/报告/调度
  的既有查询零改动。
- 已上线的链接每 14 天复检一轮（`RECHECK_AFTER_DAYS`）；复检未命中只统计
  **首次 live 之后** 的 missing，确认前的未命中不会把已交付链接拽进人工。
- 每条 live 链接都有公开、防篡改的证据页 `/evidence/<plan>.<hmac>`
  （`src/osched/evidence.py`）：listing 地址、锚文本、rel 属性
  （dofollow/nofollow）、首次发现时间、最近 12 次复检、检查时的页面指纹。
  免登录；URL 不可猜且与单一 plan 绑定。签名密钥：`EVIDENCE_SECRET`
  环境变量，缺省在 data_root 自动生成持久密钥文件（0600）。
- 暴露位置：门户实链台账（receipt 列）、客户报告（receipt URL 行）、
  CLI `osched evidence-url <plan_id>`。
- 竞品注记：单纯「live 监控」已不是差异点（ShipDR 每 6 小时复检、
  Pitchbox 有逐链健康监控）。真正的楔子是**公开可验证的证据页** +
  不 live 不计费 + 复检序列自然产出的链接存活曲线。

## B2. 客户报告（优先级 2）

面向客户的 run_log 过滤视图：提交数、成功率、**实链清单**、待客户决策项。
按周/月摘要直发客户汇总邮箱。

- 建立在：report.py 五段式骨架 + 过滤/渲染层 + report.email（客户邮箱的
  汇总角色）。
- 价值：续费沟通载体；落地 client-intake §3 的「客户报告」条目。

## B3. 目录账号生命周期（优先级 3）

大量目录要求先注册账号才能提交。把注册角色邮箱的链路闭合：自动收验证信
（IMAP）、激活账号、凭据台账、老账号复用换量。

- 建立在：contact-email 资产（注册角色）+ SMTP/IMAP 凭据模型
  （config 里 `email_code_imap` 已预留）。
- 价值：解锁大批「需注册」目录；账号成为可复用资产。

## B4. 可投递性画像与模板归因（优先级 4）

把执行失败原因聚合（bot-blocked / captcha / 无表单 / 4xx）成每域名
「可投递性画像」，反哺 min_score 和排除清单；wave2 多模板轮换按通过率
归因。

- 建立在：run_log 已记录全部失败明细——纯聚合层。
- 价值：配额有限（域名 100 地址/天），把额度花在能通过的站点上。

## B5. 多客户运营视图（优先级 5）

按客户聚合总表：pending / confirmed / 已提交 / 实链 / 人工待办，加客户级
SLA（每日最低提交数）与不达标预警。

- 建立在：project + plan 表；纯查询层。
- 价值：三个模拟客户已暴露的需求；规模化前的运营底座。

## B6. 竞品驱动的供给刷新（优先级 6）

WDC 竞品收割从手动导入升级为定时刷新：新目录自动入池 → probe → match →
待确认队列，人只做 confirm。

- 建立在：import 链路 + cron `pipeline` 段已留位。
- 价值：外链供给不断档。

## 邮箱角色模型背景（client-intake §5.4 已定稿）

客户邮箱承担两种角色——注册（contact-email 资产）与阶段性汇总
（report.email），一个邮箱可同时兼任。B2 的收件人是汇总角色，B3 的凭据
是注册角色。将来拆成两个邮箱只改配置。

## 战略背景（2026-11-18 拍板）

- **为什么做这个**：服务的站点要过 AdSense 审核、靠自身流量增长；外链
  是这一目标的流量引擎。商业层每个功能都回溯到「更多真实链接，向客户
  证明」。
- **运营形态**：后台跑 fly.io（HTTP 侧 pipeline + cron + sqlite 卷），
  完全脱离智能体平台运行（任何环节无平台依赖）。CUA（真 Chrome 验证
  码）前期留在本地服务现有站点、商业初期可接受；后期替换为开源或商用
  验证码方案（唯一接触点 §7.1 路由）。职责矩阵见 docs/deployment.zh.md。
- **AI 层（后期）**：后台将加入 AI 用于客户需求/案例对接、策划、能力
  对接。AI 只作为现有 CLI/DB 契约的调用方，不绕过人工闸。挂接点表见
  docs/deployment.zh.md。

## 竞品格局与市场裁决（2026-11-18 定稿）

范围：2C/2B × 海外/国内。对外链工具市场做了结构化扫描，结论收敛为
对定价、打包与验证码替换计划有约束力的判断。

### 市场矩阵

| 象限 | 现有玩家 | 卖什么 | 我们的裁决 |
|----------|-------------------|----------------|----------------|
| 海外 2C 工具 | 开源采集/提交器、浏览器自动化框架 | 免费自助工具 | 不做——免费/开源已把低端打到 $0 |
| 海外 2B SaaS | Respona、Pitchbox 类外联平台 | 按 link 计费约 $100–500，加活动管理 | 只做定价锚；我们的差异点是**实链闭环**（提交→回访→验证上线），扫描范围内没有竞品把它产品化 |
| 海外 2B 代做 | 外链代发服务商 | 按 link 交付，人工质检 | 我们服务档位的直接定价参照 |
| 国内 2C | 该品类不存在 | — | 无目录外链品类 |
| 国内 2B | 友链交换生态（平台+人工换链） | 友链位，不是目录提交 | 不同品类；不是竞品，是可选供给渠道 |

### 判断

1. **不做 2C 工具。** 开源层已是零价，付费 2C 工具没有楔子。工具只留
   内部自用。
2. **卖 2B 服务，对标 Resona 级 SaaS 定价。** 市场锚点约 $100–500/实链。
   我们的筹码是证据：实链台账（B1）+ 客户报告（B2）能证明链接存在——
   扫描范围内没有竞品自动闭合这个环。
3. **CUA 替换候选：开源真 Chrome 引擎。** 已定稿的「验证码留桌面」阶段
   有具名继任者——开源、以 MCP 接口暴露的真 Chrome 自动化引擎（即商业
   「AI 浏览器操作员」产品背后的那一类引擎）。接口与 §7.1 路由接触点
   兼容，替换是配置级改动。商业量起来后再评估切换。
4. **池子是长期资产。** ~55k 目录池 + probe_cache 判定史随每次运行
   复利增长；这是新进入者装个工具抄不走的护城河。
5. **国内市场：无目录品类。** 国内需求由友链生态承接。把国内当作可能的
   供给或转售渠道，而不是产品市场。

### 定价（2026-11-18 定稿）

模式：**按交付实链计价，不做订阅。** 打包为月度额度包——`quota_total`=
套餐大小，只有 `live` 判定消耗额度（门户 View A 按此实现）。

锚点：Respona 级 SaaS $100–500/link；代做服务商按条交付、人工质检。
我们的定位：**比 SaaS 档便宜的每实链价格 + 比代做档更硬的上线凭证**
（实链台账 + 客户报告就是开票凭证——只对验证上线的链接收费）。

档位（推荐默认值，数字可调）：

| 档位 | 月度规模 | 每实链价格 | 说明 |
|------|----------|-----------:|------|
| 试用 | 3 条 | 免费 | 门户自助，14 天窗口，按「邮箱 + 站点 + 网络」各限一次（见 §试用防刷） |
| 入门 | 1–9 条 | $80 | 低于 $100–500 锚点下限 |
| 成长 | 10–49 条 | $65 | 主力商业档 |
| 规模 | 50+ 条 | $50 | 走量下限；覆盖池子边际质量 |

服务保障：自动重试 + 人工兜底后仍未到 `live` 的链接**不计费**。
非 live 状态（`missing`/`unreachable`/`bot-blocked`）属进行中，
永不计费。

### 试用防刷（2026-11-18 定稿）

免费试用 = 3 条实链，是价目表上唯一「不付钱也能拿到」的东西。因此
只有三个信号**同时是新的**，项目才发放试用，且每次发放都写进
`trial_ledger`：

| 信号 | 归一规则 | 限制 |
|------|----------|------|
| 邮箱 | 小写、去 `+tag`、gmail 去点、googlemail≡gmail | 一个邮箱终身一次 |
| 站点 | 可注册域（eTLD+1）、去 `www.`、IDNA | 一个站点一次；子域归到父域 |
| 网络 | 客户端 IP（`Fly-Client-IP` / `CF-Connecting-IP`） | 一个 IP 跨所有账号一次 |

拒发不是死路：项目照常激活，只是从 0 额度起步，原因写进
`project_request.trial_note`，超管后台可见。人工审批保留邮箱／站点
校验，只跳过网络规则（审批时拿到的是运营者的 IP，不是客户的），
运营者可复核后手动设额度。

建号也受限：同一 IP 24 小时内最多注册 5 个（白名单邮箱豁免），
一个账号最多同时持有 5 个未验证草稿项目。

**是执行，不只是记账。** `quota_total` 是硬上限：排期侧拒绝排超剩余
额度的计划（`generate_plan`），执行侧拒绝跑超剩余额度的计划
（`due_today`）；一条实链恰好吃掉一个额度（`quota_used` 镜像
`plan.state='live'`）。没有门户请求的项目（自有站、导入）不受限；
`quota_type='internal'` 的自有站同样不受限。

对商业模式的直接后果：「3 条免费」无法靠开新号、换邮箱别名、把站点
拆成子域来刷，任何优惠都不会变成无限免费工。

### 品牌（2026-11-18 定稿）

**LinkAttest** — 生产域名 `linkattest.com`（whois 确认未注册；购买
待办，属用户外部动作）。名字直接编码差异点：*every link attested
live*——实链台账就是出证，出证就是开票引用的凭证。内部仓库/代号
（`outreach-scheduler`、`osched`）不变，品牌只做对外门面。

用品牌语表述定位公式：**比 Respona 级 SaaS 每实链更便宜，比代做
服务商出证更硬。**

### 支付（2026-11-18 定稿）

**约束：无香港主体，无海外主体。** Stripe 直连入驻需要港/美/英等
注册主体，所以在主体落地前，Stripe 自助收款路线**排除**。
竞品证据：海外 2B 卖家（代做/服务商类）用 发票 + 银行转账 +
Wise/Payoneer 收款——我们这个客单规模用不上 Stripe；2C 自助
（alternativeto/producthunt 类上架）才走 Stripe，因为那类买家在
$20–50 价位刷卡。

计费模式（按交付实链计价、无订阅、由实链台账出证）天然适配人工
2B 收款——台账本身就是发票附件。

分阶段分市场矩阵：

| 阶段 | 海外客户 | 国内客户 |
|-------|------------------|------------------|
| 现在（人工） | 发票 + 银行转账 / Wise / Payoneer；以 USD 报价 | 对公转账 + 增值税发票；以 CNY 报价（报价时锁定汇率） |
| 自助化升级 | **MoR：Paddle 或 Lemon Squeezy**——它们成为记录商户（merchant of record），承担税务/合规、收卡，以 wire/Payoneer 打款给国内主体。我方无需港/美主体。 | 不变：对公转账保留（国内 2B 买家默认预期） |
| 仅当日后出现海外主体 | 可在 MoR 之外加 Stripe Invoicing（此前不加） | 不变 |

决策规则：

1. 套餐申请（门户）→ 管理员标记完成 → **线下收款**
   （转账/Wise/对公）→ 管理员设置付费额度。已交付的闭环就是人工
   阶段的支付流程，无需接网关。
2. 人工阶段**不接支付网关**——申请闭环本身就是契约；网关带来
   PCI/订阅面，而我们不卖订阅。
3. 量起来需要自助结账时，只选一个 MoR（优先 Paddle：B2B 发票与
   结账本地化更强；Lemon Squeezy 更简单但发票能力薄）。只把入门档
   产品化；成长/规模档保持报价制（量级谈判本身就是价格的一部分）。
4. 国内与海外**台账永不混用**：分开报价、分开币种、分开开票。
